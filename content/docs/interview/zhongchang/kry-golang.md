### 1. 对 SQLite 数据库有了解吗？

答：SQLite 是一个轻量级的嵌入式关系型数据库，整个数据库通常就是一个文件，不需要单独启动数据库服务，适合客户端本地存储、小型工具、测试环境、低并发写入场景使用。

它支持 SQL、事务、索引和常见的约束，部署成本很低。但 SQLite 的写入并发能力有限，同一时刻写操作通常需要串行处理，不适合高并发写入或多个服务实例同时频繁修改同一个数据库文件的场景。另外，如果数据库文件放在网络文件系统上，锁机制可能不可靠。

面试中可以结合自己的使用经验补充：例如是否用它做过本地缓存、配置存储、单机日志或测试替身；如果没有实际使用过，也可以说明主要使用 MySQL 等服务端数据库，并了解 SQLite 的定位差异。

### 2. 你平时使用哪些数据库比较多？

答：这个问题应按真实项目经验回答，不能编造。可以先说最熟悉的数据库，例如 MySQL，再说明具体使用场景，例如业务数据存储、事务处理、索引设计和慢查询排查。

如果还接触过 Redis，可以补充它主要用于缓存、分布式锁、计数器或排行榜；如果用过 PostgreSQL、MongoDB、ClickHouse 或 SQLite，也可以分别说明选择原因和使用场景。最后可以总结自己的选型思路：关系型数据优先考虑事务和一致性，高并发读缓存考虑 Redis，非结构化或分析型数据再评估其他数据库。

### 3. MySQL 性能调优怎么做？

答：MySQL 性能调优通常先定位瓶颈，再从 SQL 语句、索引、表结构和数据库配置四个层面优化。

首先是通过慢查询日志、`EXPLAIN`、监控指标和数据库状态找出耗时 SQL。使用 `EXPLAIN` 重点看是否走索引、扫描行数是否过大、是否出现全表扫描或临时表排序。

SQL 和索引层面，应避免在索引列上使用函数或隐式类型转换，避免不必要的 `SELECT *`，合理设计联合索引，把等值查询和高选择性条件放在合适位置，同时注意最左前缀原则。分页查询要避免超大偏移量，可以改用基于游标的分页方式。

表结构层面，应选择合适字段类型，避免过大字段影响查询和内存使用；大字段可以考虑拆表。写入量大的场景要控制单表规模，必要时做分库分表或归档历史数据。

配置和架构层面，可以调整连接数、缓冲池大小、日志刷新策略等参数，但要基于实际负载和机器资源调整，不能盲目照抄配置。高并发场景还可以引入缓存、读写分离或异步写入，但这些方案会带来一致性、延迟和运维复杂度问题，需要结合业务要求选择。

最后，调优应量化验证，例如对比优化前后的执行时间、扫描行数、QPS 和资源占用，确认问题确实得到改善。
